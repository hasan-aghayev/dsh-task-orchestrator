## Актуализация динамической очереди — 2026-09-16

Для локального профиля проверен NInfer с `--max-context 98304`, `--kv-capacity 98304`, `--max-concurrency 2`, `--pending-timeout-ms 180000`, `--device-state-slots 0`, `--max-private-continuations 2`, Host KV 16 GiB и восемью Host State slots. Сервер сообщает `max_model_len=98304` и остаётся доступен после запуска.

Профиль DSH `web-multiagent-3090` оставлен запущенным на порту 3080; его локальный провайдер `ninfer-3090` отвечает через тот же NInfer endpoint, а короткий запрос через `/v1/chat/completions` вернул HTTP 200 и содержимое `Готово`.

Гибридный режим устроен по ходам: поток ответа родительского оркестратора завершается на вызове инструмента, затем workers используют общий бюджет `totalContextTokens`; после их завершения инструмент возвращает отчёт, и родитель продолжает работу новой генерацией. Поэтому один родительский запрос может использовать почти весь 96K предел в solo-режиме, а при делегировании тот же предел расходуется на выбранные worker-задачи и их резервы.

Шесть независимых запросов с бюджетом 8 000 токенов завершились с HTTP 200; суммарное время — 50,21 с. Повторный независимый запуск шести запросов по 16 000 токенов также завершил все шесть запросов с HTTP 200 за 100,55 с. Ранее зафиксированные 17,67 с для шести 16K использовали одинаковый префикс, поэтому отражают повторное использование приватного продолжения и не используются как независимый benchmark. Смешанный запуск `32 000, 32 000, 8 000, 8 000, 8 000, 8 000` завершил все шесть запросов; два больших запроса прошли через очередь, максимальное время ответа составило около 104 с.

Первый вариант с восемью приватными продолжениями оставлял четыре запроса 16K в ожидании после заполнения пула. Ограничение до двух приватных продолжений устранило этот сценарий; состояния workers не теряются, а новые задачи запускаются после освобождения активного места.

Workflow-планировщик изменён с ожидания всей партии на динамическое пополнение: освободившийся слот получает следующий подходящий worker при сохранении зависимостей, конфликтов записи, двух активных генераций и общего бюджета `totalContextTokens`. Плагин: `pnpm check`, `pnpm test` — 14 тестов проходят; добавлен тест, который подтверждает запуск следующего worker до завершения медленного соседа.

Фактическая параллельность NInfer остаётся верхней границей: в независимом смешанном запуске prefill наблюдался по одному активному запросу, хотя допускаются два. Это снижает скорость, но не нарушает корректность очереди; шесть workers завершаются последовательно и не превышают лимит памяти.

## Актуализация 96K adaptive policy — 2026-09-17

Эта секция является текущим источником истины для локального профиля. Ранние разделы выше сохраняются как исторические замеры и намеренно содержат старые кандидаты 65K, 80K и 110K.

Профиль `web-multiagent-3090` использует `hardContextTokens: 98304` и `totalContextTokens: 98304`, то есть общий логический предел 96K. Worker получает минимальный подходящий уровень из `8192`, `16384`, `24576`, `32768`, `49152`, `65536`, `81920` и `98304`; уровень 81K/96K не резервируется заранее и выбирается только для конкретной задачи.

План строится до шести логических workers, но допускает сначала `preferredWorkers: 2`. После завершения уже запущенной задачи scheduler добавляет следующий готовый worker, если выполнены зависимости, общий бюджет и лимит активных генераций. Reviewer остаётся обычным worker и не создаёт седьмой слот. Поэтому один оркестратор может работать один, а затем перейти к смешанному режиму с частью workers без копирования всей родительской истории.

Перед передачей отчёта зависимой задаче и перед повторной попыткой `NEED_MORE_CONTEXT` применяется детерминированная компактизация: сохраняются идентификатор и статус, итог, находки, доказательства, изменённые файлы, тесты, блокеры, следующие шаги и потребность в продолжении; длинные поля ограничиваются `contextCompactionChars: 4096`. Это ограничение размера сообщения, а не обещание семантически идеального резюме.

В коде очереди есть карта `concurrencyByContext`, поэтому другой профиль может разрешить больше активных малых workers после отдельного benchmark. Для текущей RTX 3090 с Vision, MTP, INT8 KV и 96K NInfer надёжно запускается с `--max-concurrency 2` и `--max-private-continuations 2`. Запуск с тремя активными генерациями завершился ошибкой резервирования runtime-памяти: требовалось `5172210944` байт при доступных `5119275008`; вариант с шестью требовал `5937268224` при тех же доступных `5135396864`. Профиль поэтому оставлен на двух активных запросах для всех малых уровней и одном для 65K–96K; значения 3–6 не объявляются безопасными на этой карте.

После изменений адресные тесты плагина покрывают расширенные уровни контекста, безопасные значения карты по умолчанию, динамическое расширение с двух до шести малых workers, общий бюджет, compaction зависимостей и освобождение очереди; текущий набор содержит 18 тестов. Физическая concurrency выше двух не подтверждена и не используется в локальном профиле.
