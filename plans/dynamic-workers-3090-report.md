# Отчёт реализации dynamic-workers-3090

Дата: 2026-09-16. Отчёт отделяет выполненные проверки от ещё не измеренных.

## HARDWARE

RTX 3090: 24 576 MiB VRAM. В исходном моментальном замере было занято 21 389 MiB. Windows сообщала около 47,8 GiB RAM, WSL — около 46 GiB доступной общей памяти. Запас VRAM измерялся после старта каждого отдельного процесса NInfer.

## MODEL

Модель `/home/diffusionlab/ninfer/models/qwen3_8_27b.ninfer`, серверное имя `qwen3.8-27b`. Модель, формат весов, vision и MTP не менялись. Исполняемый файл `/home/diffusionlab/ninfer/ninfer-serve` имеет SHA-256 `a84bae658fe67017dd13807570330adcc97e976bcea4fab1c28e47158d75dd76`, совпадающий со сборкой из commit `75d94eab17619bf3723a8d66e1881a6673bc25ee`.

## NINFER

Проверены локальные `--help`, `/health`, `/v1/models` и реальные Responses/Chat Completions. Рабочий кандидат использует `--max-context 65536 --kv-capacity 81920 --max-concurrency 2 --kv-dtype int8 --device-state-slots 2 --host-state-slots 8 --host-kv-mib 16384 --max-private-continuations 8 --max-shared-prefixes 8`. `/health` возвращает `{"status":"ok"}`, модель сообщает `max_model_len: 65536`.

## DSH

Исходный DSH остаётся на commit `da4bebc8e7457ff07431a19a5c1ac9cf0111bc03` с прежними незакоммиченными изменениями. Отдельный плагин подключён локальной ссылкой в профиле `web-multiagent-3090`; рабочая ветка плагина — `codex/dynamic-workers-3090` с одним локальным commit реализации. Экспериментальная копия в DSH не заменялась.

Эффективный dump профиля показывает `preferredWorkers: 2`, `maxWorkers: 6`, `maxTotalAgents: 7`, `maxConcurrentAgents: 2`, `maxActiveGenerations: 2`, `hardContextTokens: 65536`, `priorityAgingMs: 30000`. Новый чистый браузерный сеанс через этот профиль получил `Full access`, вызвал `task_orchestrate` и показал `1 subagent running`; plan-only вызов вернул план.

## MEMORY ARCHITECTURE

Добавлен `ResourceManager`, который ограничивает только время потребления model stream. Ожидание инструментов и дочерних задач слот не занимает. Очередь имеет приоритет пользовательского запроса перед worker и FIFO внутри уровня; долго ожидающие записи повышают приоритет через `priorityAgingMs`. Отмена до допуска удаляет запись, исключения и нормальное завершение освобождают слот. До отправки выполняется консервативная оценка токенов; точным остаётся токенизатор NInfer.

Проверка KV: `65536` оставила 1,85 GiB VRAM после старта, `81920` — 1,28 GiB с 8 GiB host KV, `98304` — 799 MiB, `114688` — 166 MiB. Поэтому 80K выбран кандидатом, а 96K и 112K не объявлены устойчивыми. Вариант 80K с host KV 16 GiB запустился; его текущий процесс оставлен для дальнейших проверок.

## CACHE TEST

В Responses API повторный запрос с `previous_response_id` в той же последовательности получил `prefix_reuse_path: private_turn_closure`, 1 133 cached input tokens и TTFT 0,36 с против 1,45 с у первого запроса. На входе около 4K токенов первый TTFT был 5,09 с, продолжение — 0,285 с, cached input tokens — 4 787.

Это подтверждает повторное использование продолжения в работающем процессе. Восстановление после перезапуска, точный объём передачи из RAM и повторно обработанные токены после рестарта не измерены; в отчётах это не заменяется предположением о сохранении KV.

## PERFORMANCE

Исходный режим (`max-context 8192`, `kv-capacity 16384`, `max-concurrency 6`) на трёх одинаковых коротких Chat Completions дал TTFT 1,87/1,23/1,24 с и полное время 3,20/2,33/2,41 с. Для основных длинных сравнений трёх повторов и часовая смешанная нагрузка ещё не выполнены.

## SIX WORKER TEST

Шесть одновременных HTTP-запросов через кандидат `kv80-host16` завершились. NInfer фактически держал не более двух генераций; остальные ожидали очередь, максимальное зарегистрированное ожидание — около 10,27 с. Это проверка физической очереди запросов, а не доказательство качества шести ролей на реальной задаче.

## SINGLE VS MULTI AGENT

Сравнение качества одиночного агента с полным шестиработниковым сценарием на фиксированном аудите, измерение токенов и стоимости, а также повторяющаяся нагрузка не менее часа пока не выполнены. Браузер доказал загрузку профиля, вызов инструмента, plan-only результат и видимое состояние дочернего агента; чистый автоматический запуск с шестью исполнителями не объявляется проверенным.

Текущий совместимый workflow сохраняет отдельную модельную фазу `Planner` и необязательную фазу `Reviewer`; лимит `maxTotalAgents: 7` включает эти контрольные фазы, а при review граф получает до пяти execution-задач плюс reviewer. Это ограничение явно зафиксировано для последующей доработки, если потребуется строгое отсутствие отдельного planner-агента.

## FINAL RECOMMENDED CONFIG

Для следующего этапа оставлен профиль `web-multiagent-3090` и NInfer с 80K device KV, 16 GiB host KV, 8 host state slots и двумя активными генерациями. Конфигурация сохраняет vision, MTP, модель и INT8 KV. VRAM-запас около 1,28 GiB находится в целевом диапазоне; устойчивость на часовой смешанной нагрузке ещё не подтверждена.

## FINAL VERDICT

Реализованы и локально проверены ограничитель обращений к NInfer, динамический предел работников, зависимости существующего workflow, контроль размера запроса, отмена очереди, документация, план и резервная копия. Рабочий кандидат 80K/16 GiB запущен, два одновременных запроса и шесть HTTP-запросов через очередь подтверждены. Полное требование «строго один оркестратор без planner-фазы», восстановление KV после перезапуска, часовая нагрузка и сравнительный аудит качества остаются незавершёнными и должны быть закрыты отдельным этапом.
