# Измерения dynamic-workers-3090

Команды и сырые результаты этого каталога относятся к локальному NInfer на RTX 3090. Скрипт `campaign.py` запускает один процесс NInfer с явными аргументами, ждёт `/health`, выполняет одинаковые запросы и сохраняет JSONL с задержками, памятью и счётчиками очереди.

## Зафиксированные результаты

- Исходный режим (`max-context 8192`, `kv-capacity 16384`, `max-concurrency 6`): три коротких Chat Completions дали TTFT 1.87/1.23/1.24 с и полное время 3.20/2.33/2.41 с.
- Кандидат `max-context 65536`, `kv-capacity 65536`, INT8 KV, два активных запроса, 8 host slots и 8 GiB host KV запустился с 1.85 GiB свободной VRAM после запуска.
- В Responses API повторный запрос с `previous_response_id` использовал `private_turn_closure`: TTFT снизился до 0.36 с, в usage отмечено 1133 cached input tokens. Это подтверждает повторное использование продолжения в проверенной последовательности; отдельное восстановление после перезапуска ещё не измерено.
- Для 4K входа на том же кандидате первый TTFT составил 5.09 с, продолжение — 0.285 с, cached input tokens — 4787.
- `kv-capacity 81920` с 8 GiB host KV оставил 1.28 GiB VRAM; вариант с 16 GiB host KV также запустился и выбран для очередного теста.
- `kv-capacity 98304` оставил 799 MiB, что ниже целевого запаса 0.8--1.5 GiB; `114688` оставил 166 MiB и признан небезопасным.
- Шесть параллельных запросов через `kv80-host16` завершились. NInfer обслуживал не более двух одновременно, остальные ожидали в очереди; максимальное зафиксированное ожидание составило около 10.27 с.

## Ограничения измерений

Это локальные smoke и очередь-тесты, а не часовая смешанная нагрузка и не полный сравнительный аудит качества. Восстановление после перезапуска, длинные контексты 16/32/48/56K, RAM-cache 24 GiB и полный сценарий браузерного оркестрирования остаются отдельными проверками. Неизмеренные показатели не подменяются оценками.
